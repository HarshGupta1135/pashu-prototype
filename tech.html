Build notes

Pashu · how I would implement this, on the stack I work in

Four of the five features are CRUD. One — reading a handwritten prescription — is the entire engineering story, and the 30 days should be allocated accordingly.

Stack I am building this on JavaSpring Boot 3Spring SecurityJWTRESTMySQL 8RedisReactFlyway

01 Where the risk actually sits

Search, profiles, reminders and the emergency screen are well-understood request/response work. The document pipeline is the only component with genuine unknowns: input quality is uncontrolled, the output is probabilistic, and the data it produces is medical. So it gets its own week, its own staging tables, and a human confirmation step before anything is trusted.

The corollary is a scoping decision rather than a technical one: anything that competes with that week gets cut.

02 The document pipeline

The AI is not a library I import. It is one outbound HTTP call, made off the request thread, whose output I never trust blindly. Framed that way it becomes ordinary Spring work.

POST /api/v1/pets/{petId}/documents          // multipart upload
  → validate type + size, write to S3
  → INSERT document (status = QUEUED)
  → 202 Accepted { documentId }           // request thread ends here

DocumentWorker                               // @Scheduled poll, or Redis Stream consumer
  → SELECT ... FOR UPDATE SKIP LOCKED     // MySQL 8; safe with N workers
  → call Claude API with image + JSON schema
  → map → ExtractionResult, persist per-field confidence
  → status = NEEDS_REVIEW

GET  /api/v1/documents/{id}/extraction       // powers the confirm screen
POST /api/v1/documents/{id}/confirm          // promotes staging → medical_record

Three decisions that matter more than the model

  • Nothing AI-generated is written straight to the medical record. Extraction lands in a staging table; only the user’s /confirm call promotes it, in one transaction. That single rule is what makes an AI feature safe in a health product — and it is just good transaction design.
  • Confidence is stored per field, and so is the raw response. extraction_field(document_id, field_key, value, confidence, bbox), plus the raw JSON in a JSON column. When extraction quality is the core asset, the ability to reprocess old documents is the asset.
  • The dose cross-check is plain Java, not AI. Recompute mg/kg against the extracted body weight and flag any mismatch deterministically. Probabilistic extraction, deterministic validation on top — that is where I stop trusting the model.
Why the confirm step is a feature, not friction

An unclear digit in a body weight is a dosing error, not a typo. Surfacing low-confidence fields for confirmation is cheaper than any accuracy improvement, and it is the only design that stays defensible when extraction is wrong — which it sometimes will be.

The verification agent

A @Scheduled job selects providers whose verified_at is older than N days and sends a WhatsApp template message. A webhook controller receives the free-text reply, an AI call parses it into {open, hours, species}, and the listing updates. Freshness is computed from verified_at, never a stored score that can drift out of sync.

04 Auth, and why RBAC alone is not enough

Phone OTP is the only realistic first factor in India. The OTP lives in Redis with a TTL and never touches MySQL. The access JWT is short-lived (~15 min); the refresh token sits in Redis so it can actually be revoked.

Roles: PET_PARENT, VET, CLINIC_ADMIN, NGO, RESCUER, PLATFORM_ADMIN. But role checks alone will not hold — a vet who claims a listing may edit that clinic only, and a pet’s record belongs to exactly one owner. So authorization is resource-scoped:

@PreAuthorize("hasRole('PET_PARENT') and @petGuard.owns(principal, #petId)")
public PetRecordDto getRecord(@PathVariable Long petId) { ... }

@PreAuthorize("hasRole('CLINIC_ADMIN') and @providerGuard.manages(principal, #providerId)")
public void updateHours(@PathVariable Long providerId, @RequestBody HoursDto dto) { ... }

“RBAC” is a bullet everyone writes. Ownership-scoped authorization on medical data is the version that shows the problem was actually thought about.

05 Geo-search on MySQL

MySQL 8 spatial covers this without needing PostGIS. Two things trip people up, and both are worth knowing before writing the query.

Two gotchas

Axis order. With SRID 4326 MySQL follows the EPSG axis order, so it expects POINT(latitude, longitude) — not the lng/lat order most map APIs hand you.

Index usage. ST_Distance_Sphere on its own will not use the spatial index. A bounding-box prefilter does the index work; the sphere distance then orders the small result set exactly.

SELECT p.id, p.name,
       ST_Distance_Sphere(p.geo, ST_SRID(POINT(:lat, :lng), 4326)) AS metres
FROM providers p
JOIN provider_species ps
       ON ps.provider_id = p.id AND ps.species = :species
WHERE MBRContains(:envelope, p.geo)        -- uses the SPATIAL INDEX
  AND p.status = 'ACTIVE'
HAVING metres <= :radiusMetres
ORDER BY metres
LIMIT 20;

“Open now” joins provider_hours on the current weekday and time instead of interpreting a text field, which is what makes the filter trustworthy enough to show on every row.

07 How the pieces connect

A React PWA (Vite, installable — no app store, one build for both user types) talks to the Spring Boot REST API over JWT. The API owns MySQL 8 and Redis. Uploads go to S3 and return immediately; the document worker consumes the job and calls the Claude API. WhatsApp is both an outbound channel for reminders and an inbound webhook into the same API, which is what lets the verification agent close its own loop.

Integrations: Google Maps Places and Geocoding plus Plus Codes for rescue locations; WhatsApp Business Cloud API; Claude API for extraction; MSG91 for OTP delivery; Razorpay scaffolded but switched off until booking exists.

Kept because it earns its place

  • Modular monolith. One service, one database. No microservices, no Kafka at this size.
  • Testcontainers for MySQL and Redis, MockWebServer for the Claude call — the pipeline is testable without spending tokens in CI.
  • Idempotency keys on /confirm, retries with backoff on the AI call, a hard timeout, and a FAILED terminal state the user can actually see.

Cut deliberately

  • Online booking — no small practice runs a calendar, so a call button is the honest primitive.
  • Ratings — empty review counts are worse than none; freshness carries the trust instead.
  • Payments, vet-side dashboard, teleconsults, native apps, insurance, e-pharmacy, livestock, a second city, and any in-house model training.

The one metric: share of users who upload at least one record and return in week two. Not downloads. If the vault does not retain, the thesis is wrong — and 30 days is enough to find that out.
